# Real-engine gate: headless Factorio + RCON

Unit tests in `dmr-tests/` run in a Lua sandbox and **cannot** catch a bad prototype
schema or a load-order crash. Prove a mod on the real engine before shipping.

## The trap this exists for

A fix applied to the source tree **after** the zip was packed stays out of the shipped mod.
A 4.3.0 zip went out carrying a crash the source had already fixed 5 minutes later.
Rule: **gate the packaged bytes, not the source** — extract the zip into a mods dir and test that.

## Headless server (exact game version, no login needed)

1. Get the matching headless build — the version the AUTHOR's game actually runs, not the one you
   remember (see "Gate on the engine version the author runs" below) — and unpack it anywhere.
2. Per-run config so writes do not pollute `~/.factorio`:

```ini
[path]
read-data=__PATH__executable__/../../data
write-data=/abs/path/run<TAG>
[general]
locale=en
```

3. Mods dir = **the shipped zip extracted**, root renamed to `name_version`
   (Factorio refuses anything else: "Directory name of mod … doesn't match the expected … case sensitive!").
4. `mod-list.json`: list `base` + the DLC mods (`elevated-rails`, `quality`, `recycler`,
   `space-age`) + the mod, all `enabled: true`.
5. **Startup settings without a binary dat**: omit `mod-settings.dat` (defaults from
   `settings.lua` apply) or rewrite `default_value = "…"` in the extracted copy's `settings.lua`
   to exercise another mode. `mod-settings.dat` is a binary property tree — not worth writing.
6. Fresh map = the cheapest data-stage test, and it exits non-zero on error:

```bash
factorio --config runX/config.ini --mod-directory modsX --create runX/mapX.zip
# exit=1 + "Failed to load mod …: <file>:<line>: <error>" on a data-stage crash
```

7. Functional assertions need a running game (`--start-server` + `--rcon-port/--rcon-password`).
   Factorio's RCON is the standard Source protocol; a minimal client is ~50 lines of `socket`.

## RCON / Lua console quirks (2.1.20) — each one cost a run

- Bare Lua is sent as **chat**, not executed. Prefix every command with `/c `.
- The first Lua command answers *"Using Lua console commands will disable achievements.
  Please repeat the command to proceed."* → **send the same command twice**.
- Prototypes are **`prototypes.recipe / .entity / .technology / .item`** — `game.recipe_prototypes`
  no longer exists ("LuaGameScript doesn't contain key recipe_prototypes").
- No `game.write_file` / `game.table_to_json`. Use **`helpers.write_file(name, data)`** and
  **`helpers.table_to_json(t)`**; output lands in `<write-data>/script-output/<name>`.
  (The reliable way to get an answer back — `print()` does not travel over RCON.)
- `game.map_gen_presets` does not exist at runtime; read the live value with
  `settings.startup["<setting>"].value`.
- Recipe `category` (singular) is gone in 2.1 → `categories` **array**: `r.categories[1]`.
  Writing `category = "x"` is a load error, so prototypes need `categories = { "x" }`.
- `machine.energy_usage` is **J/tick**: 1 MW reads as 16666.67.
- The mod's own `helpers` functions are not on the global `helpers`; assert on prototypes and
  live settings instead of calling mod internals.

## What a good verdict looks like

One line of JSON per mode, read off disk, e.g. for a 3-mode setting:

| assertion | A | B | C |
|---|---|---|---|
| live startup setting | "Ore patches" | "Ore patches + synthesis" | "Synthesis only" |
| synthesis recipe/machine/tech | no | yes | yes |
| resource entities on a fresh map | 81 | 48 | **0** |

"as designed" + a number only the real engine can produce (ore count on a fresh map) beats any
amount of "tests pass".

## Keep the harness cheap (and survive the scratch prune)

Scratch (`~/.hermes/cache/scratch/`) is pruned after 24 h idle: run dirs, maps and dumps are *meant*
to die there and be regenerated by the driver script. The **engine itself is the exception** — keep
one extracted build per game version at `~/.hermes/tools/factorio-<version>/` (confirm with
`<path>/bin/x64/factorio --version`), so a release gate can be re-run on demand without a 60–100 MB
re-download, and so audits can prove presence by pointing at a stable path.

Pitfall: a subagent asked whether an engine exists searches the path it remembers, fails, and writes
"no Factorio binary on this host" into its report. An absence claim is unproven until you run the
one command that settles it (`ls <known path>`, `<known path>/bin/x64/factorio --version`) — and
when you falsify one, append the correction to that report file, because it is about to be merged
into a brief.

## Gate on the engine version the AUTHOR runs

The headless build you gate with must be the game version the author is playing. The mod was
gated on 2.1.20 for a week while the author had moved to a fresh 2.1.23 experimental install —
"it loads on 2.1.20" is not a claim about 2.1.23, and the author will meet your gap first.

- Read the version off the author's install (or ask) before downloading; a new build is one
  request: `https://factorio.com/get-download/<ver>/headless/linux64` → `tar.xz`, ~60-100 MB.
- Confirm the unpacked binary really is that version: `<path>/bin/x64/factorio --version`.
- Re-run the FULL gate (data stage + dump assertions) on the new build before publishing.
  Prototype schemas and validation do change between patches, and a green old-gate says
  nothing about the new one.

## Data-stage probe mod: cheaper than a dump for a handful of assertions

To verify what a mod SHIPS at the data stage — recipe counts, `energy_required`,
`allow_productivity`, which items landed in which category — you rarely need the 122 MB
`data-raw-dump.json`. A throwaway probe mod in the same mods dir runs AFTER the mod under
test and answers in one grep.

1. `mkdir <mods-dir>/zzz-probe_0.0.1` — the `zzz-` prefix makes it load last among mods.
2. `info.json`: `{"name":"zzz-probe","version":"0.0.1","factorio_version":"2.1",
   "dependencies":["<mod-under-test>"]}` — declare the dependency so ordering is guaranteed
   by the engine, not by the sort key.
3. `data-final-fixes.lua` walks `data.raw`, filters by a name pattern, and emits one
   `log("P1 " .. ...)` line per fact (counts, per-item times, a category histogram).
4. `factorio --mod-directory <mods-dir> --dump-data > run.log 2>&1` — `--dump-data` is the
   cheapest run that exercises every data stage and still writes the full dump if you later
   need it.
5. `grep 'P1 ' run.log` — the probe's lines, filtered out of the mod's own warnings.

Probe rules:

- **A probe cannot `require` the mod's internals.** `package.loaded["lib.timing-model"]`
  returns `false` from another mod's file even though that mod just loaded it — each mod's
  module namespace is its own. Recompute the fact from `data.raw` inside the probe (build
  the ingredient lists, the producer map, the depth table — 30 lines of Lua beats a
  dependency on private state you do not control).
- **Copying a SOURCE tree into a mods dir needs the same rename as a zip extract** — and
  the target name tracks that tree's `info.json`, which changes on every build: copy as
  `<name>_<version-from-that-tree>`, and re-copy rather than reusing an older dir.
- **Probe output belongs on `log()` with a unique prefix.** `helpers.warn` writes into the
  same log stream as real engine diagnostics, so a `grep -c ' Warning '` health count stops
  meaning "the engine is clean".
- **Read the field you actually mean**: recipe `categories` = which machine can craft it,
  recipe `subgroup` = which picker row it lands in.
- The probe is disposable: it lives in the scratch mods dir, never in the shipped zip. Keep
  one stable copy beside the engine (`~/.hermes/tools/dmr-probe/`) since scratch is pruned
  in 24 h — it is the expensive half of the harness, like the engine itself.
- A probe that only counts is still a verdict: "249 recipes before, 254 after" settles a
  generation change the way no source diff can.

## Runtime proof: a probe mod + `--benchmark`, not just a dump

`--dump-data` proves the DATA stage only. It cannot prove a runtime mechanic — research
productivity, a machine's real craft rate, an effect multiplier — because none of those exist
until a game is running. A dump that looks perfect while the mechanic silently does nothing is
the failure mode this closes.

The pattern that settles it: a ~30-line **probe mod** in the mods dir beside the mod under test,
whose `control.lua` builds the exact scenario in `on_init` / `on_nth_tick` (place the machine,
insert fuel, grant the researched techs, run N ticks) and `print("[PROBE] ...")` one line per
checkpoint. `print` reaches the log in both run modes, so no server and no RCON are needed:

```bash
factorio --config runX/config.ini --mod-directory modsX --create runX/mapX.zip   # data + on_init
factorio --config runX/config.ini --mod-directory modsX --benchmark runX/mapX.zip --benchmark-ticks 4200
```

Read the `[PROBE]` lines off stdout: `tick=3600 coal=10 finished=10` on a 20 s recipe means 4
items per craft — the productivity multiplier genuinely pays out. Until a number like that
exists, "research productivity applies to replication" is an assertion, not a result.

Keep the probe mod beside the engine (`~/.hermes/tools/dmr-probe/`), the same way the engine
itself is kept: scratch is pruned in 24 h and the probe is the expensive half of the harness.
